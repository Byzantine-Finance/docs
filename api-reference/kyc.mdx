---
title: "Individuals - KYC"
---

In order to use the Byzantine Prime application, an individual user needs to go through a KYC process. This is a regulatory obligation for individuals.

<Info>
  Before creating the individual account, the user must accept the required terms. See [Terms and Conditions](/api-reference/terms-and-conditions).
</Info>

### 1. Create the individual account

The creation of the individual account is done by calling this API endpoint:

<Card icon="arrow-right" horizontal href="/api-reference/customer-management/create-individual-account" title="Create an individual account">

</Card>

An individual account is described by two distinct fields:

- **`userInfo`** - the person being verified. They are the KYC subject and the account's customer.
- **`rootUsers`** - the signer(s) who control the account. Each root user holds their own passkey and can sign transactions, exactly like the root users of an entity account. Every entry carries its own `firstName`, `lastName`, `email`, and `authenticators`.

For a standard, self-created account, the account holder is both the verified customer and the signer - include the **same person in both `userInfo` and `rootUsers`, using the same email**.

Only the following fields are required to create the account:

- `firstName`, `lastName`, `email` (in `userInfo`)
- one signer in `rootUsers` (`firstName`, `lastName`, `email`)
- `byzantineTermsSignedAt`

Two optional fields can also be set on creation or later through the update endpoint:

- `accountPurpose` - `investment_purposes`, `protect_wealth`, `personal_or_living_expenses` or `other`, with `accountPurposeOther` describing it;
- `fiatCurrencies` - the fiat rails the customer will use: `usd` requests the `base` endorsement, `eur` the `sepa` endorsement. It defaults to both.

The account receives an `accountId`, and every person on it gets their own `userId`: one for the verified customer in `userInfo`, and one for each signer in `rootUsers`. In a standard self-created account, `userInfo` and the single root user are the same person, so there is just one `userId`.

<Warning>
  To register a passkey at account creation, provide the `authenticators` inside the corresponding `rootUsers` entry. If no passkey is added at creation, OTP authentication is automatically set up for that user - and OTP will then be required to add a passkey later through a dedicated endpoint.
</Warning>

<Note>
  An individual account can have **more than one signer**, and you can create an account **on behalf of a client** (for example as a wealth manager / CGP) by verifying one person in `userInfo` while a different person signs via `rootUsers`. See [Multi-users account](/api-reference/multi-users-account).
</Note>

### 2. Complete the application

The rest of the KYC (personal data, ID document, proof of address, questionnaires) can be completed in two ways:

- **Through the API**: you collect the data and documents in your own interface and send them to Byzantine.
- **In the Sumsub Web SDK**: the customer provides them directly in the [Sumsub](https://docs.sumsub.com/docs/get-started-with-web-sdk) verification interface (ID scan, selfie, proof of address), so you have nothing to collect yourself.

You can combine both: whatever has already been submitted is kept and never asked again. For example, send the personal data you already hold through the API, then let the Web SDK collect the documents.

#### Through the API

Once the account is created, use the update endpoint to progressively provide the remaining information needed for KYC verification:

<Card icon="arrow-right" horizontal href="/api-reference/customer-management/update-an-individual-accounts-user-details" title="Update an individual account">

</Card>

The following information can be submitted via one or multiple update calls:

- Personal data (date of birth, nationality, address, phone number, etc.). Include `nationalities`, every nationality held, which is required for EEA residents, and `cityOfBirth`, recommended for EEA residents and required by EU law from 2027. `countryOfBirth` is required for EEA residents.
- Additional information in `additionalUserInfo`, when requested. `actingAsIntermediary: true` is refused: customers sending or receiving funds on behalf of someone else cannot be onboarded.
- ID documents (passport, national ID card, driver's licence or residence permit). See the [list of accepted documents](/api-reference/accepted-documents)
- Proof of address, issued within the last 90 days. See the [list of accepted documents](/api-reference/accepted-documents)

<Warning>
  Customers residing in New York cannot be onboarded: a US residential address in the state of New York is refused.
</Warning>

<Info>
  The response of both the create and update endpoints will include a `missingDocuments` field listing any remaining required items that have not yet been submitted: `IDENTITY_DOCUMENT`, `PROOF_OF_ADDRESS_DOCUMENT`, `RESIDENTIAL_ADDRESS` or `ADDITIONAL_USER_INFO`.
</Info>

#### In the Sumsub Web SDK

Open a verification session for the account:

<Card icon="arrow-right" horizontal href="/api-reference/customer-management/initialize-a-verification-session" title="Initialize a verification session">

</Card>

`mode` decides how you show the Web SDK to your customer:

| `mode` | You get | Valid for | Best for |
| --- | --- | --- | --- |
| `link` | `verificationUrl`, a page hosted by Sumsub | 24 hours | No integration at all |
| `access_token` | `accessToken`, for the Sumsub Web SDK | 10 minutes | A verification embedded in your own frontend |

<Tabs>
  <Tab title="link">
    `verificationUrl` is a plain URL, so use it however fits your flow: redirect your customer to it, open it in a new tab, display it in an `<iframe>`, or send it by email or message.

    Optionally set `language` for the page language, and `successUrl` / `rejectUrl` (HTTPS) to bring the customer back to your app once they have submitted, or if the verification is refused.

    <Tip>
      In an `<iframe>`, allow the camera so the customer can scan their ID document and take the selfie: `<iframe src="{verificationUrl}" allow="camera; microphone"></iframe>`.
    </Tip>
  </Tab>
  <Tab title="access_token">
    The `accessToken` only works with the Sumsub Web SDK, which you install in your frontend: from npm (`npm i @sumsub/websdk`, or [`@sumsub/websdk-react`](https://www.npmjs.com/package/@sumsub/websdk-react) for React) or with a `<script>` tag. Sumsub's [Web SDK integration guide](https://docs.sumsub.com/docs/get-started-with-web-sdk) covers the installation and the customisation options.

    <Warning>
      Skip the step of Sumsub's guide that generates the access token through the Sumsub API: Byzantine generates it. Call `init-verification` from your backend, since it is signed with your integrator key, and pass only the `accessToken` to your frontend.
    </Warning>

    ```js
    import snsWebSdk from '@sumsub/websdk';

    // accessToken: returned by init-verification, called by your backend
    const sdk = snsWebSdk
      // Called by the SDK when the token expires (after 10 minutes): have your backend
      // call init-verification again and resolve with the new accessToken.
      .init(accessToken, () => fetchNewAccessTokenFromYourBackend())
      .withConf({ lang: 'en' })
      .build();

    sdk.launch('#sumsub-websdk-container');
    ```
  </Tab>
</Tabs>

Byzantine does not store the link or the token: when one expires, call `init-verification` again for a new one. Once the verification is under review, approved or finally rejected, the endpoint returns `409`. Follow the progress through the [customer webhooks](/api-reference/webhooks/customers) or with the user details (step 3).

### 3. Read the current user details

Use the user-details endpoint to retrieve the current KYC information and the accounts associated with the person:

<Card icon="magnifying-glass" horizontal href="/api-reference/customer-management/get-details-of-a-single-user" title="Get user details">

</Card>

The response's `userInfo` includes `firstName`, `lastName`, and `email`, plus the available optional fields: `middleName`, `phone`, `birthDate`, `nationality`, `countryOfBirth`, and `residentialAddress`. `nationalities` and `cityOfBirth` can be submitted but are not returned.

Once the customer is registered with Bridge, the account reads ([Get account details](/api-reference/account-management/get-details-of-a-single-account) and the accounts returned with the user details) include `fiatRequirements`, which lists what the USD (`base`) and EUR (`sepa`) rails still need. See [Fiat requirements](/api-reference/kyb#5-fiat-requirements) for how to read it.

### 4. KYC verification

Byzantine and Bridge will verify the individual's identity and address. Both Bridge and Byzantine may ask for additional details during this process.

Byzantine does not email the customer about the verification: follow its status with the [customer webhooks](/api-reference/webhooks/customers), and notify the customer from your app when needed. See [Verification statuses](/api-reference/verification-statuses) for the meaning of each status.

<Info>
  The KYC process usually takes only a few minutes.
</Info>
